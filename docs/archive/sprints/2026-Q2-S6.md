# Sprint 2026-Q2-S6

**Status:** ✅ Closed 2026-06-16 — goal met. Frozen.
**Window:** 2026-06-13 → 2026-06-27
**Goal:** Make the live **maestro → lead → Workflow → user** loop reliable
end-to-end. S5 proved the Workflow *engine* is solid, but the 016/018 live
smoke showed the **maestro turn/gate/messaging layer is rough**: a maestro
couldn't address its own lead, long Workflow turns false-timed-out, and a
maestro can't bridge an interactive gate back to your phone. S6 hardens that
layer — bridge maestro gates to the user, stop long Workflow turns from
false-timing-out, fix lead addressing, route maestro→user messages
first-class, and auto-recover jammed sessions — so a phone-driven orchestration
loop holds up. (Phase 3 **Track 2**, the debate/blackboard/tournament
interaction-pattern library, builds on this foundation in S7.) In parallel — on
surfaces that don't touch the maestro-loop files — S6 also governs the now-live
worktree floor (**024** project ownership / PA write-policy, **025**
crash-recovery) and adds a maestro **phase-confirmation gate** (**019**, a
deliberate human checkpoint before a maestro executes), built on 029's fixed
bridge.

## Risks

- **Overlapping bridge surface.** 029 (gate→user), 021 (maestro→user), and 030
  (turn liveness) all touch the reader / pty_session / notification path. Land
  029 first to establish the bridge, then 021/030 on top; watch for churn in
  `pty_session.py` and the gate coordinator.
- **030 vs 017.** 030 may reopen 017's liveness-reset — confirm whether the
  reset never armed on Workflow progress or fires too coarsely before patching.
- **Behaviour, not deletion.** Unlike S5's subtractive work, S6 changes live
  maestro behaviour — every ticket needs a deployed re-smoke, not just green
  unit tests.
- **019 is the spill candidate.** It's the only blocker-bearing ticket (needs
  029) and design-heavy/ADR-worthy; if S6 overruns, **019 carries to S7** — its
  029 dependency means it starts last anyway.
- **024 / 025 are the safe parallel lanes.** Pulled in as independent side-work;
  they touch the permissions / worktree subsystems, not the maestro-loop files,
  so they never collide with 020/021/029/030/031.

  user on Telegram, holds the Turn open, and the user's answer is injected back
  — verified on deployed code (029).
- A long Workflow turn that completes is **accepted**, not false-timed-out
  (030); a genuinely jammed session is auto-bounced (020).
- A maestro reliably addresses its own lead; maestro→user messages deliver
  first-class (031, 021).
