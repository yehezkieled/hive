# Sprint 2026-Q2-S6

**Status:** Active
**Window:** 2026-06-13 → 2026-06-27
**Goal:** Make the live **maestro → lead → Workflow → user** loop reliable
end-to-end. S5 proved the Workflow *engine* is solid, but the 016/018 live
smoke showed the **maestro turn/gate/messaging layer is rough**: a maestro
couldn't address its own lead, long Workflow turns false-timed-out, and a
maestro can't bridge an interactive gate back to your phone. S6 hardens that
layer — bridge maestro gates to the user, stop long Workflow turns from
false-timing-out, fix lead addressing, route maestro→user messages
first-class, and auto-recover jammed sessions — so a phone-driven orchestration
loop holds up. (Phase 3 **Track 2**, the debate/blackboard/tournament
interaction-pattern library, builds on this foundation in S7.)

## Committed

- [`029-maestro-gate-bridge-regression`](../tickets/029-maestro-gate-bridge-regression/) ✱
  — a maestro `AskUserQuestion` / `ExitPlanMode` gate must reach the user on
  Telegram and hold the Turn open (Ticket 003 bridge gap). The 028 guard
  defused the *danger* (no phantom-answer); 029 restores the *capability*.
  **022** (research-delegation gate) likely folds in here.
- [`030-workflow-turn-no-progress-timeout`](../tickets/030-workflow-turn-no-progress-timeout/)
  — the 180s no-progress reader timeout false-fires on long Workflow turns even
  when the run succeeds; 017's liveness-reset isn't fully holding. Found by the
  016/018 live smoke.
- [`031-maestro-lead-addressing`](../tickets/031-maestro-lead-addressing/)
  — a maestro addresses its own lead as `self.<team>` instead of
  `<maestro>.<team>`, so the delegation message dies with `Unknown recipient`.
  A `self`/`me` alias or stricter addressing guidance. Found by the smoke.
- [`021-router-user-queue`](../tickets/021-router-user-queue/)
  — route maestro→user messages first-class (today a non-Telegram path logs
  `Unknown recipient: user`); the user is a real delivery target, not a gap.
- [`020-adapter-liveness-escalation`](../tickets/020-adapter-liveness-escalation/)
  — auto-bounce a jammed PTY session instead of stranding the Turn; the
  recovery half of the timeout/jam class that 030 diagnoses.

## Risks

- **Overlapping bridge surface.** 029 (gate→user), 021 (maestro→user), and 030
  (turn liveness) all touch the reader / pty_session / notification path. Land
  029 first to establish the bridge, then 021/030 on top; watch for churn in
  `pty_session.py` and the gate coordinator.
- **030 vs 017.** 030 may reopen 017's liveness-reset — confirm whether the
  reset never armed on Workflow progress or fires too coarsely before patching.
- **Behaviour, not deletion.** Unlike S5's subtractive work, S6 changes live
  maestro behaviour — every ticket needs a deployed re-smoke, not just green
  unit tests.

## Out of scope

  (debate / blackboard / tournament) and the skills routing Leads to them. S7,

- **019** (maestro phase-confirmation gate), **024** (project ownership & PA

## Definition of done

- A maestro interactive gate (`AskUserQuestion` / `ExitPlanMode`) reaches the
  user on Telegram, holds the Turn open, and the user's answer is injected back
  — verified on deployed code (029).
- A long Workflow turn that completes is **accepted**, not false-timed-out
  (030); a genuinely jammed session is auto-bounced (020).
- A maestro reliably addresses its own lead; maestro→user messages deliver
  first-class (031, 021).
- `ruff` + full `pytest -m "not integration"` green; a deployed
  maestro→lead→leaf→**user** round-trip completes with a maestro gate bridged.
- INDEX rows for 020–021 + 029–031 reflect final state.
